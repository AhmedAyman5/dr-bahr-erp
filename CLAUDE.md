## 1. What this project is

- The frontend of **Dr. Bahr ERP**, for an Egyptian import & distribution company (NOT a medical system).
- Stack: **React 19 + Vite + JavaScript (JSX) + Tailwind CSS v4 + React Router + Axios + lucide-react (icons)**.
- The UI is **Arabic only, RTL**. Code (files, variables, functions, comments) is **English**.
- The backend is a separate NestJS API built by Mazen. The backend owns business logic, calculations, validation and the database. The frontend displays data, collects input, calls the API, and handles loading / error / empty / success states.
- The code must stay **simple and beginner-friendly**. The developer is learning React: readable code beats clever code.

Team: Ahmed = frontend, Mazen = backend. Work is delivered in weekly chunks: each week Mazen finishes a backend part + docs, then the frontend builds its pages.

### Backend rules every page must respect (from week1 overview)

1. Every success response is `{ message, data }`. Lists → `data` is an array (`[]` when empty). Delete → `data` is `null`.
2. **Unknown fields in a request body → 400.** Build every body explicitly from form fields. Never send `id`, `code`, `createdAt`, `updatedAt`, `deletedAt`, `lastLoginDate`, or nested objects (`category`, `product`, `inventory`, ...). IDs that belong in the URL (e.g. `branchId`) never go in the body.
3. `code` is generated by the server → show it **read-only**, never send it.
4. Money / quantity values are **sent as numbers** but **returned as strings** (`"12.5"`). Convert with `Number(...)` before sending or calculating; display with `formatNumber`.
5. Delete is always a soft delete. Deleted records disappear from lists and get-by-id returns 404.
6. `PATCH` is partial — send only the editable fields.
   **Emptied optional fields**: on PATCH an optional field the user emptied is sent as **`null`**
   (null clears it; `""` is never sent). On create an empty optional field is **left out**. Never send `null` for a
   required field or a money / number field (send `0`) → 400. Use `optionalField(value, isEdit)` from `utils/body.js`.
   The nullable fields: branch `address` · customer `taxNumber`, `commercialRecord`, `phone`, `address` · supplier
   `taxNumber`, `contactPerson`, `phone`, `email` · employee `nationalId`, `jobTitle`, `hireDate` · product `barcode` ·
   user `email`, `employeeId`, `branchId`.
   Exception — user links: on PATCH `employeeId` / `branchId` are sent **only when changed in the form**, so a user
   whose linked employee was deleted later can still be saved (the deleted id is never sent back → no 400).
7. Only SUPERADMIN can call the API for now (others get 403).
8. Enum fields (e.g. product `itemType`: `STOCK` / `SERVICE`) are **sent and compared as the English value** and **displayed with the Arabic label** from the docs.
9. Every error body is `{ statusCode, message, error, code, field }`. `code` is stable; `message` may change. Translate errors with `code` + `field`, never by parsing `message`.

### Week 2 rules (purchasing + stock) — details in `../backend/doc/week2/week2flow.txt`

1. **Stock is always in the PRIMARY unit** (pieces), even when buying in cartons (`baseQuantity` = quantity × factor).
   Documents show quantities in the line's unit; stock screens and the item card show pieces.
2. **Only the server moves stock.** Every change is a stock movement (`OPENING`, `ADJUSTMENT`, `PURCHASE`, ...;
   `MOVEMENT_TYPES` in `utils/labels.js`). There is no "create movement" screen; refresh stock screens after an action.
   Manual stock edit = **تسوية** (adjustment): `reason` (max 250) is required when quantity or cost changes.
   `costPrice` is the weighted **average** cost ("متوسط التكلفة").
3. **The server computes ALL totals.** The UI may show a live preview while typing, but always displays the server's
   values after saving. Never send totals (`subTotal`, `taxValue`, `netTotal`, `lineTotal`, `baseQuantity`, ...),
   `code`, `status` or `createdBy` (only a fixed header `discountValue` may be sent, §9). Status changes only
   through the action endpoints (post / cancel / status).
4. **POSTED documents are read-only** (no edit / delete); they can only be cancelled. CANCELLED is read-only too.
   Show the buttons from the state machines (week2flow §6) and a `StatusBadge` on every document and list row.
5. **Paginated lists**: `?page=&pageSize=` (pageSize 1–100) → `data = { items, meta: { page, pageSize, total,
   totalPages } }`. Use `hooks/usePaginatedData` + `components/ui/Pagination`. Week 1 lists stay plain arrays.
6. **Line errors** use field `"lines.N.<field>"` (N from 0): `getErrorMessage` shows "البند رقم N+1: ...",
   `getLineError(err)` → `{ lineIndex, field }` to highlight the row.
7. **Dates** are sent as `"YYYY-MM-DD"` and come back as `"YYYY-MM-DDT00:00:00.000Z"`: use the first 10 characters
   (never a `Date` object, so the day never shifts with the time zone).
8. Document numbers (`PQ-2026-000001`, `PI-...`, `PR-...`) are generated by the server: read-only, never sent.
   The one exception to "never send `code`": a currency's `code` (EGP, 3 capital letters) is typed by the user.

## 5. Page anatomy (the core rule)

Each page lives in its own folder and is independent from other pages.

**`pages/Branches` is the reference CRUD page.** New list pages copy its structure:
`<Name>.jsx` (list page: data from `useLoadData`, success message from `useAutoHideMessage`, `refresh()` after
add / edit / delete) + `<name>Api.js` + `components/<Name>FormModal.jsx` (add + edit in one modal) + `e2e/<name>.spec.js`.

```text
pages/Products/
├── Products.jsx              # UI + Tailwind classes + page state + event handlers
├── productsApi.js            # ALL backend calls for this page (and nothing else)
├── components/               # OPTIONAL — only when Products.jsx gets big (~250+ lines)
│   └── ProductFormModal.jsx  #   page-specific pieces, never imported by other pages
└── assets/                   # OPTIONAL — only if the page has its own images
```

### `<Page>.jsx`

- Uses `useState`, the shared hooks from `src/hooks/` (loading data: see below), simple functions, simple conditional rendering.
- Calls functions from its own `<page>Api.js` only. No axios / `api` import in JSX files.
- Must render the 4 states: **loading**, **error (with retry)**, **empty**, **data**. Use the shared state components.
- Search / filtering of lists is done on the client (the API has no pagination yet).

### `<page>Api.js` — the page's contract with the backend

- Imports the shared instance: `import api from "../../services/api";`
- Each function **returns the payload (`response.data.data`)**, so pages never see axios responses.
- Each function that sends a body **builds it explicitly** from the form values (so unknown fields are never sent, numbers are converted). Optional fields go through `optionalField(value, isEdit)`: left out on create when empty, `null` on edit when emptied (null clears the saved value). Money stays a number (`0` when empty), never `null`.
- No React state, no UI logic, no `try/catch` (errors bubble up to the page).
- Dropdown data for this page (e.g. categories for the product form) is fetched by functions in **this** file — small duplication between pages is OK; importing another page's API file is not.

```javascript
// pages/Branches/branchesApi.js
import api from "../../services/api";
import { optionalField } from "../../utils/body";

// Optional fields: left out on create when empty; null on edit when emptied (null clears them).
function toBranchBody(form, isEdit) {
  return {
    name: form.name.trim(),
    address: optionalField(form.address, isEdit),
  };
}

export async function getBranches() {
  const response = await api.get("/branch");
  return response.data.data;
}

export async function createBranch(form) {
  const response = await api.post("/branch", toBranchBody(form, false));
  return response.data.data;
}

export async function updateBranch(id, form) {
  const response = await api.patch(`/branch/${id}`, toBranchBody(form, true));
  return response.data.data;
}

export async function deleteBranch(id) {
  await api.delete(`/branch/${id}`);
}
```

### Standard data-loading pattern — `hooks/useLoadData` + `hooks/useAutoHideMessage`

Pages never write their own loading code, success-message timer or `useEffect` for loading. They use the two hooks:

```javascript
// One list (see pages/Branches)
const { data, loading, error, refreshError, reload, refresh } = useLoadData(getBranches);
const branches = data ?? []; // data is null until the first answer

// Several lists: one loader OUTSIDE the component that returns an object (see pages/Inventories)
async function loadPageData() {
  const [inventories, branches] = await Promise.all([getInventories(), getBranches()]);
  return { inventories, branches };
}
const { data, ... } = useLoadData(loadPageData);
const inventories = data?.inventories ?? [];

// Load again when a value changes — deps are simple values (see pages/ProductStock)
useLoadData(async () => (activeId ? getStock(activeId) : []), [activeId]);

// Success message that hides by itself after 4 seconds
const [successMessage, showSuccessMessage, hideSuccessMessage] = useAutoHideMessage();

// Week 2 paginated list (data = { items, meta }): page / pageSize / filters go in the query string.
// The API function receives { page, pageSize, ...filters } (empty filters removed) — see the hook's comment.
const { items, meta, filters, loading, error, refreshError, reload, refresh, setPage, setPageSize, setFilters } =
  usePaginatedData(getPurchaseInvoices, { status: "" });
<Pagination meta={meta} onPageChange={setPage} onPageSizeChange={setPageSize} />
```

- `loading` → `<LoadingState />` · `error` → `<ErrorState onRetry={reload} />` · `refreshError` → `<Alert type="error">`.
- `reload()` = the retry button: shows LoadingState again.
- `refresh()` = **silent**: the table stays on screen (no LoadingState, no jump to the top) while the new data loads.
  After every add / edit / delete call `refresh()`, never `reload()`. If a refresh fails, the old data stays
  and `refreshError` explains it.
- An answer that arrives after a newer request started is ignored (fast switching in ProductStock).
- `usePaginatedData`: `setFilters({ status })` **merges** into the filters and goes back to page 1 (so does
  `setPageSize`); a page that no longer exists after a `refresh()` (its last row was deleted) jumps to the last page.
- No `eslint-disable` anywhere in `src/`: the hooks are written so the `react-hooks` lint rules pass.

### Adding a new page — checklist

1. Read the module doc(s) in `../backend/doc/`.
2. Create `pages/<Name>/<Name>.jsx` and `pages/<Name>/<name>Api.js`.

## 6. Core infrastructure (built once — reuse it)

### `services/api.js`

- `baseURL` comes from `import.meta.env.VITE_API_URL` — never hard-code a URL.
- Request interceptor adds `Authorization: Bearer <token>` from `session.js`.
- Response interceptor: on **401** (except the login request) → `clearSession()` and go to `/login`.
- Pages and API files never read the token or set headers themselves.

### Environment

- `.env.local` (git-ignored, each developer has their own) → `VITE_API_URL=http://localhost:3000`.
- `.env.example` (committed) is the template: same keys, safe example values.
- **There is no deployed backend right now.** Development and testing use the local Docker backend only. The Railway URL that still appears in the backend docs is dead — ignore it and never use it.
- When a production backend exists later, its URL will be set as `VITE_API_URL` in the hosting dashboard (e.g. Vercel → Settings → Environment Variables), not in any committed file.
- Vite reads env vars at start/build time: restart `npm run dev` (or redeploy) after changing them.
- Everything starting with `VITE_` ends up in the browser bundle → never put secrets in it.

### Auth

- Login: `POST /auth/login` with `{ username, password }` → response `data = { access_token, user: { id, username, role } }`.
- `session.js` exports `saveSession(token, user)`, `getToken()`, `getUser()`, `clearSession()`, `isLoggedIn()`.
- `/login` is public and outside `MainLayout`. All other pages are protected by `ProtectedRoute`.
- Logout lives in the Header only: `clearSession()` → navigate to `/login`.
- `/auth/signup` is TEMPORARY on the backend — never build a signup screen.
- Route access checks (logged in / logged out / role) live inside guard components (`ProtectedRoute`, `PublicOnlyRoute`, `RoleRoute`) so they run on every render. Never compute them inline in `AppRoutes` JSX — the value goes stale and can cause redirect loops.

### Roles — `routes/rolePages.js`

- `ROLE_PAGES` maps each role to the page paths it may open: `{ SUPERADMIN: ["*"], ADMIN: [], ACCOUNTANT: [], SALES: [], USER: [] }`.
  `canAccess(role, path)` checks it; the home page `/` is always allowed.
- The Sidebar shows only allowed links (empty groups are hidden). Opening a non-allowed page by URL shows
  "ليس لديك صلاحية لعرض هذه الصفحة" (`RoleRoute` → `pages/NoPermission`) with a link to the home page.
- Until Week 5 only SUPERADMIN can use the API. **Opening pages per role in Week 5 = edit `ROLE_PAGES` in this one file**
  (e.g. `ACCOUNTANT: ["/customers", "/suppliers"]`). Do not add role checks anywhere else; do not invent permissions.

### Postponed (backend does it at the end of the project — frontend keeps blocking)

The backend does NOT prevent these yet, so the frontend must keep blocking them:
- a user deleting their own account, or changing their own role (Users page: disabled + note);
- deleting or demoting the LAST SUPERADMIN;
- deleted users keep their `employeeId` / `email`, so the same employee / email cannot get a new account
  (409 `BELONGS_TO_DELETED`: field `employeeId` → "هذا الموظف مرتبط بمستخدم محذوف", field `email` →
  "هذا البريد مرتبط بمستخدم محذوف"; other fields → the generic `ERROR_AR` message).

### Week 1 screens changed by Week 2 (week2flow §12)

- ProductStock: the edit action is **"تسوية الرصيد"** (`SlidersHorizontal` icon): required "سبب التسوية" (max 250)
  with quick-pick chips (جرد / تالف / خطأ في الإدخال); only the changed quantity / cost is sent, + `reason`;
  حفظ is disabled while nothing changed. `costPrice` is labelled "متوسط التكلفة". SERVICE products stay hidden in "add".
- Products: the edit form loads `GET /products/:id`; a non-empty `units` array → the primary unit is read-only with
  the note "لا يمكن تغيير الوحدة الأساسية بعد استخدام الصنف (له حركات مخزن أو وحدات)" (stock movements can't be
  known in advance: the backend's 400 covers them).
- Item Units: the in-use delete message also covers product units.

### Errors — `utils/errors.js`

`getErrorMessage(error, options)` always returns an **Arabic** string, built from `error.response.data.code` + `error.response.data.field` (codes: `../backend/doc/week1/00-overview.txt` + `../backend/doc/week2/00-overview.txt`):

- `ERROR_AR` map: one Arabic message per `code` (`VALIDATION_FAILED`, `DOES_NOT_EXIST`, `BAD_REQUEST`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `ALREADY_EXISTS`, `BELONGS_TO_DELETED`, `INTERNAL_ERROR`, Week 2: `INVALID_STATUS`, `INSUFFICIENT_STOCK`, `QUANTITY_EXCEEDED`), using `{field}` as a placeholder. Use the Arabic texts from the backend doc.
- `FIELD_AR` map: Arabic label per field name (from the module docs). Unknown field → a neutral Arabic fallback ("أحد الحقول"), never raw English.
- `CODE_FIELD_AR` map: one exact message for a `"<code>:<field>"` pair (header fields only), e.g.
  `"BAD_REQUEST:primaryItemUnitId"`. A message that only makes sense on one form stays in that form
  (e.g. `VALIDATION_FAILED` + `reason` in ProductStock's `StockFormModal`, because returns also have a `reason`).
- Line fields `"lines.N.<field>"` → "البند رقم N+1: <message with the label of <field>>". `getLineError(error)`
  → `{ lineIndex, field }` (or `null`) so a document form can highlight that row.
- No response at all (server down / network) → "تعذر الاتصال بالخادم، تحقق من الاتصال وحاول مرة أخرى".
- Login screen: `UNAUTHORIZED` → "اسم المستخدم أو كلمة المرور غير صحيحة" (pass an option like `{ context: "login" }`).
- Unknown / missing `code` → the `INTERNAL_ERROR` message.
- `DOES_NOT_EXIST` = an id in the body points to a missing **or deleted** record → "<field label> غير موجود أو محذوف"
  (e.g. "الفرع غير موجود أو محذوف"). Forms with dropdowns (Products, ProductStock, Users) then keep the form open
  with the error, clear that choice and call `onRefreshLists()` → the page's silent `refresh()`, so the deleted
  item disappears from the Select.
- `BAD_REQUEST` + field `branchId` (Users) → "فرع المستخدم يجب أن يكون نفس فرع الموظف".
  Never show raw English backend messages to the user. Add new codes/field labels to the maps when new docs arrive.

### Formatting — `utils/format.js`

- `formatNumber(value)` → handles string numbers from the API, Arabic-friendly output with Western digits (`ar-EG-u-nu-latn`, e.g. `1,234.5`).
- `formatMoney(value, { maxDecimals })` → money columns: always 2 decimals, Western digits, thousands separator, no currency symbol (`"1500"` → `1,500.00`, `"-250.5"` → `-250.50`, empty / invalid → `-`). Use it for **every** money value. In tables render it inside `<span dir="ltr">` so the minus of a negative value stays on the left in RTL.
  - `maxDecimals` (default `2`) is for `Decimal(18,4)` columns (product prices): at least 2, at most 4 decimals → `formatMoney("15", { maxDecimals: 4 })` = `15.00`, `formatMoney("12.3456", { maxDecimals: 4 })` = `12.3456`.
- `formatDate(value)` → readable date with Arabic month names and Western digits (`ar-EG-u-nu-latn`, e.g. `21 نوفمبر 2026`).

### Money inputs — `utils/money.js`

Money columns in the DB are `Decimal(18,2)` (customers, suppliers) or `Decimal(18,4)` (product prices, `reorderLimit`). Every money field in a form follows the same rules:

- The form keeps the typed text (`useState` string). Add mode starts at `"0"`; edit mode starts with the API string (`"1500.5"`). An empty field means 0. Exception: a **required** money field (product prices) starts empty in add mode and is checked with "السعر مطلوب" before `validateMoney`.
- Input: `<Input inputMode="decimal" dir="ltr" ... />` (label stays Arabic). Phone, email, tax number and commercial record inputs also get `dir="ltr"`.
- `validateMoney(text, { min, maxDecimals })` in the form's `validate()` → Arabic error or `""`. Checks: a valid number, max `maxDecimals` decimals (default `2`), max `18 - maxDecimals` digits before the point, and `min` when given (mirror the backend: e.g. `{ min: 0 }` for `@Min(0)`, no `min` when negative values are allowed).
- `toMoneyNumber(text, { maxDecimals })` in the page's `<page>Api.js` body builder → a number (`""` → `0`), rounded to `maxDecimals` (default `2`). Money is never sent as a string.
- `Decimal(18,4)` fields pass `{ maxDecimals: 4 }` to all three helpers (see `pages/Products`).

## 8. Arabic, RTL & design

- `index.html` has `<html lang="ar" dir="rtl">`. Do not add `dir` on components.
- Every user-facing string is Arabic: labels, buttons, placeholders, table headers, empty/error/loading text, confirmations. Use natural, short business Arabic (e.g. "إضافة فرع", "حفظ", "إلغاء", "جارٍ التحميل...").
- API field names stay as they are in code; only the displayed labels are Arabic.
- Prefer logical Tailwind utilities (`ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`, `text-start`) over `ml/mr/pl/pr/left/right`.
- Font: Cairo (loaded in `index.html`, set as `--font-sans`).
- Icons: `lucide-react` only (e.g. `import { Plus, Pencil, Trash2 } from "lucide-react"`). Directional icons (arrows, chevrons) must point the right way in RTL.

### Design tokens (defined once in `src/index.css` with `@theme`)

| Token class                                                               | Meaning                        |
| ------------------------------------------------------------------------- | ------------------------------ |
| `bg-primary`, `hover:bg-primary-hover`, `text-primary`, `bg-primary-soft` | main blue actions / active nav |
| `bg-slate-50`                                                             | app background                 |
| `bg-white` + `border-slate-200`                                           | cards, tables, modals          |
| `text-slate-900` / `text-slate-500`                                       | main / secondary text          |
| `red-600` / `red-700`                                                     | danger                         |

| `bg-sky-600` / `bg-violet-600` + `text-white`                             | sky = مدين (debit) · violet = دائن (credit) — reserved for debit/credit only, never used for anything else |

**Document status colors** — only in `StatusBadge` (soft background + border + dark text, `rounded-full text-xs`;

| ---------------------------------------- | ------------------------------------------------ | -------------------------------- |
| DRAFT مسودة                              | `border-slate-200 bg-slate-100 text-slate-700`   | saved, no effect yet             |

Use `primary` tokens instead of `blue-600` so the brand color can change in one place. Style: clean, calm, professional ERP — light shadows, `rounded-lg`, no gradients, no heavy animations. Must work on desktop, laptop and tablet.

### Usability rules (users are accountants, not developers)

- Every clickable element shows a pointer cursor (global rule in `index.css`); disabled shows `not-allowed`.
- Colors have one fixed meaning and are never mixed: blue (`primary`) = main / safe action, red = destructive or leaving (delete, logout), green = success, amber = warning, gray/slate = neutral or cancel, sky / violet = مدين / دائن badges only, purple = CONVERTED status only (see the status table above). Never use red for a normal action or blue for a destructive one.
- Every destructive or session-ending action (delete, logout, discarding unsaved changes) asks for confirmation with `ConfirmDialog`; the confirm button is red and names the action (e.g. "حذف الفرع", "تسجيل الخروج"), never a vague "تأكيد" or "نعم".
- All interactive elements have clear hover and keyboard focus states.
- Icon-only buttons have an Arabic `title` (tooltip) and `aria-label`, e.g. `title="تعديل"`.
- Buttons use clear Arabic verbs that say what will happen ("حفظ", "إضافة صنف", "حذف").
- Modals close only with X / إلغاء / Escape — never by clicking the backdrop.
- Numbers and dates are shown with Western digits (123).
- **Balances (debit / credit)** use the standard accounting labels and are always shown in full — never a tooltip,
  never a bare minus sign:
  - in tables: the amount **without its sign** (`text-sm font-semibold`) + a solid badge "مدين" (**sky**:
    `bg-sky-600 text-white`) or "دائن" (**violet**: `bg-violet-600 text-white`), both
    `rounded-full px-2.5 py-0.5 text-sm font-bold`, no border; and a second line in small gray text with
    the plain meaning (e.g. "على العميل لنا"). Debit / credit is a direction, not good or bad: never red / green.
    0 → "0.00" with no badge. Use `BalanceCell` (the colors live only there).
  - in forms: under the balance input a short gray hint on how to type the sign, and a **live preview** that updates
    while typing ("سيتم تسجيله: 250.50 دائن — للعميل علينا"; nothing for empty / 0 / invalid). Use `BalancePreview`.
  - the sign → { label, meaning } logic lives only in `getBalanceSide(value, party)` (`utils/labels.js`):
    customer + = مدين "على العميل لنا", − = دائن "للعميل علينا" · supplier + = دائن "علينا للمورد", − = مدين "لنا عند المورد".
- Every action gives visible feedback: loading state while waiting, a success message after, an Arabic error if it fails.

## 10. Testing

- A task is NOT done until `npm run build`, `npm run lint` and `npm run test:e2e` all pass.
- Every new page gets an e2e test file: the page loads with no console errors, the main happy path works (e.g. list → add → edit → delete with confirmation), and the Arabic error / empty states show.
- Every bug fix gets a regression test that fails before the fix and passes after it.
- Tests fail on any console error or page error coming from the app.
- Plain functions (`utils/`) may get Node-only unit checks (`e2e/errors.spec.js`: `test` from `@playwright/test`, no
  page). Shared components and hooks are tested through real pages — never through a test-only route.
- Stock movements are never deleted (backend rule): tests that add stock leave movements on soft-deleted test products.
- **The database is NOT empty**: it holds the demo data (`npm run seed:demo`) and EGP (the default currency).
  Tests must never modify or delete demo records or EGP: they create their own tagged records and clean up ONLY those.
  Never assume an empty list or "the only branch / warehouse": empty states, "auto-select the single warehouse" and
  similar cases are tested with mocked API answers (`page.route`).
- Leftover checks compare snapshots, never expect empty lists: `e2e/global-setup.js` snapshots every list (+ the
  stock of every warehouse) before the run and fails the run if, after it, a record was left behind, or a record
  that existed before was deleted or modified (`updatedAt` / `lastLoginDate` ignored).
- Playwright runs with `workers: 4` (more parallel browsers overload the machine: `ERR_INSUFFICIENT_RESOURCES`).
- Never weaken, skip or delete a test to make it pass; fix the real cause.
- Tests that need the backend skip with a clear message when the API is down — tell Ahmed.
- Do not change `../backend` or its data beyond what a test needs through the API.
- In the final report, list: tests run, passed, skipped (and why), and any console warnings seen.
