# CLAUDE.md — Dr. Bahr ERP (Frontend)

Read this file fully before writing any code. It is short on purpose: every rule here matters.

## 1. What this project is

- The frontend of **Dr. Bahr ERP**, for an Egyptian import & distribution company (NOT a medical system).
- Stack: **React 19 + Vite + JavaScript (JSX) + Tailwind CSS v4 + React Router + Axios + lucide-react (icons)**.
- The UI is **Arabic only, RTL**. Code (files, variables, functions, comments) is **English**.
- The backend is a separate NestJS API built by Mazen. The backend owns business logic, calculations, validation and the database. The frontend displays data, collects input, calls the API, and handles loading / error / empty / success states.
- The code must stay **simple and beginner-friendly**. The developer is learning React: readable code beats clever code.

Team: Ahmed = frontend, Mazen = backend. Work is delivered in weekly chunks: each week Mazen finishes a backend part + docs, then the frontend builds its pages.

### ⛔ The backend folder is off-limits

`../backend/` belongs to Mazen. Ahmed owns the frontend only.

- You may **READ** `../backend/` (docs and code) to understand the API. That is all.
- **Never** create, edit, move or delete any file inside `../backend/` — not even a typo fix, a comment, a doc note or a `.env` file. This applies to every tool: file edits, shell commands (`sed`, `echo >`, `rm`, `mv`, ...), and git commands run inside it.
- If something in the backend looks wrong or is missing, **stop and report it to Ahmed** (what, where, and a suggested fix). Ahmed will tell Mazen. Never work around a backend bug by changing backend code.

Before building or changing a page, read: every `../backend/doc/FRONTEND_WEEKN_*.txt` update file for that week (oldest first), then `../backend/doc/weekN/00-overview.txt` (if present), then the module file(s) for that page. When an update file and a module file disagree, the newest update file wins — mention the conflict to Ahmed.

- Never invent endpoints, fields, query params or business rules. Use exact URLs and field names as documented.
- If something is missing or unclear in the docs, **stop and ask** instead of guessing.
- Never copy response shapes from memory or from old code — always from the current docs.

### Backend rules every page must respect (from week1 overview)

1. Every success response is `{ message, data }`. Lists → `data` is an array (`[]` when empty). Delete → `data` is `null`.
2. **Unknown fields in a request body → 400.** Build every body explicitly from form fields. Never send `id`, `code`, `createdAt`, `updatedAt`, `deletedAt`, `lastLoginDate`, or nested objects (`category`, `product`, `inventory`, ...). IDs that belong in the URL (e.g. `branchId`) never go in the body.
3. `code` is generated by the server → show it **read-only**, never send it.
4. Money / quantity values are **sent as numbers** but **returned as strings** (`"12.5"`). Convert with `Number(...)` before sending or calculating; display with `formatNumber`.
5. Delete is always a soft delete. Deleted records disappear from lists and get-by-id returns 404.
6. `PATCH` is partial — send only the editable fields.
7. Only SUPERADMIN can call the API for now (others get 403).
8. Enum fields (e.g. product `itemType`: `STOCK` / `SERVICE`) are **sent and compared as the English value** and **displayed with the Arabic label** from the docs.
9. Every error body is `{ statusCode, message, error, code, field }`. `code` is stable; `message` may change. Translate errors with `code` + `field`, never by parsing `message`.

## 5. Page anatomy (the core rule)

Each page lives in its own folder and is independent from other pages.

**`pages/Branches` is the reference CRUD page.** New list pages copy its structure:
`<Name>.jsx` (list page) + `<name>Api.js` + `components/<Name>FormModal.jsx` (add + edit in one modal) + `e2e/<name>.spec.js`.

```text
pages/Products/
├── Products.jsx              # UI + Tailwind classes + page state + event handlers
├── productsApi.js            # ALL backend calls for this page (and nothing else)
├── components/               # OPTIONAL — only when Products.jsx gets big (~250+ lines)
│   └── ProductFormModal.jsx  #   page-specific pieces, never imported by other pages
└── assets/                   # OPTIONAL — only if the page has its own images
```

### `<Page>.jsx`

- Uses `useState` / `useEffect`, simple functions, simple conditional rendering.
- Calls functions from its own `<page>Api.js` only. No axios / `api` import in JSX files.
- Must render the 4 states: **loading**, **error (with retry)**, **empty**, **data**. Use the shared state components.
- Search / filtering of lists is done on the client (the API has no pagination yet).

### `<page>Api.js` — the page's contract with the backend

- Imports the shared instance: `import api from "../../services/api";`
- Each function **returns the payload (`response.data.data`)**, so pages never see axios responses.
- Each function that sends a body **builds it explicitly** from the form values (so unknown fields are never sent, numbers are converted). An optional text field the user emptied is sent as `""` so PATCH can clear it.
- No React state, no UI logic, no `try/catch` (errors bubble up to the page).
- Dropdown data for this page (e.g. categories for the product form) is fetched by functions in **this** file — small duplication between pages is OK; importing another page's API file is not.

```javascript
// pages/Branches/branchesApi.js
import api from "../../services/api";

function toBranchBody(form) {
  return {
    name: form.name.trim(),
    address: form.address.trim(), // "" when emptied — undefined would make PATCH keep the old value
  };
}

export async function getBranches() {
  const response = await api.get("/branch");
  return response.data.data;
}

export async function createBranch(form) {
  const response = await api.post("/branch", toBranchBody(form));
  return response.data.data;
}

export async function updateBranch(id, form) {
  const response = await api.patch(`/branch/${id}`, toBranchBody(form));
  return response.data.data;
}

export async function deleteBranch(id) {
  await api.delete(`/branch/${id}`);
}
```

### Standard data-loading pattern

```javascript
const [branches, setBranches] = useState([]);
const [loading, setLoading] = useState(true);
const [error, setError] = useState("");

async function loadBranches() {
  setLoading(true);
  setError("");
  try {
    setBranches(await getBranches());
  } catch (err) {
    setError(getErrorMessage(err));
  } finally {
    setLoading(false);
  }
}

useEffect(() => {
  // Loading data on mount is the normal use of an effect; the lint rule cannot tell.
  // eslint-disable-next-line react-hooks/set-state-in-effect
  loadBranches();
}, []);
```

The `eslint-disable` line is needed: the `react-hooks/set-state-in-effect` rule flags any function
that sets state when it is called from an effect, even when the state is set after `await`.

### Adding a new page — checklist

1. Read the module doc(s) in `../backend/doc/`.
2. Create `pages/<Name>/<Name>.jsx` and `pages/<Name>/<name>Api.js`.
3. Add the route inside the `MainLayout` group in `routes/AppRoutes.jsx`.

## 6. Core infrastructure (built once — reuse it)

### `services/api.js`

- `baseURL` comes from `import.meta.env.VITE_API_URL` — never hard-code a URL.
- Request interceptor adds `Authorization: Bearer <token>` from `session.js`.
- Response interceptor: on **401** (except the login request) → `clearSession()` and go to `/login`.
- Pages and API files never read the token or set headers themselves.

### Environment

- `.env.local` (git-ignored, each developer has their own) → `VITE_API_URL=http://localhost:3000`.
- `.env.example` (committed) is the template: same keys, safe example values.
- **There is no deployed backend right now.** Development and testing use the local Docker backend only. The Railway URL that still appears in the backend docs is dead — ignore it and never use it.
- When a production backend exists later, its URL will be set as `VITE_API_URL` in the hosting dashboard (e.g. Vercel → Settings → Environment Variables), not in any committed file.
- Vite reads env vars at start/build time: restart `npm run dev` (or redeploy) after changing them.
- Everything starting with `VITE_` ends up in the browser bundle → never put secrets in it.

### Auth

- Login: `POST /auth/login` with `{ username, password }` → response `data = { access_token, user: { id, username, role } }`.
- `session.js` exports `saveSession(token, user)`, `getToken()`, `getUser()`, `clearSession()`, `isLoggedIn()`.
- `/login` is public and outside `MainLayout`. All other pages are protected by `ProtectedRoute`.
- Logout lives in the Header only: `clearSession()` → navigate to `/login`.
- `/auth/signup` is TEMPORARY on the backend — never build a signup screen.
- No role-based UI yet. Keep `user.role` stored; do not invent permissions.
- Route access checks (logged in / logged out) live inside guard components (`ProtectedRoute`, `PublicOnlyRoute`) so they run on every render. Never compute them inline in `AppRoutes` JSX — the value goes stale and can cause redirect loops.

### Errors — `utils/errors.js`

`getErrorMessage(error, options)` always returns an **Arabic** string, built from `error.response.data.code` + `error.response.data.field` (see `../backend/doc/FRONTEND_WEEK1_UPDATE_2.txt`, PART 4):

- `ERROR_AR` map: one Arabic message per `code` (`VALIDATION_FAILED`, `DOES_NOT_EXIST`, `BAD_REQUEST`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `ALREADY_EXISTS`, `BELONGS_TO_DELETED`, `INTERNAL_ERROR`), using `{field}` as a placeholder. Use the Arabic texts from the backend doc.
- `FIELD_AR` map: Arabic label per field name (from the same doc). Unknown field → a neutral Arabic fallback ("أحد الحقول"), never raw English.
- No response at all (server down / network) → "تعذر الاتصال بالخادم، تحقق من الاتصال وحاول مرة أخرى".
- Login screen: `UNAUTHORIZED` → "اسم المستخدم أو كلمة المرور غير صحيحة" (pass an option like `{ context: "login" }`).
- Unknown / missing `code` → the `INTERNAL_ERROR` message.
  Never show raw English backend messages to the user. Add new codes/field labels to the maps when new docs arrive.

### Formatting — `utils/format.js`

- `formatNumber(value)` → handles string numbers from the API, Arabic-friendly output with Western digits (`ar-EG-u-nu-latn`, e.g. `1,234.5`).
- `formatMoney(value, { maxDecimals })` → money columns: always 2 decimals, Western digits, thousands separator, no currency symbol (`"1500"` → `1,500.00`, `"-250.5"` → `-250.50`, empty / invalid → `-`). Use it for **every** money value. In tables render it inside `<span dir="ltr">` so the minus of a negative value stays on the left in RTL.
  - `maxDecimals` (default `2`) is for `Decimal(18,4)` columns (product prices): at least 2, at most 4 decimals → `formatMoney("15", { maxDecimals: 4 })` = `15.00`, `formatMoney("12.3456", { maxDecimals: 4 })` = `12.3456`.
- `formatDate(value)` → readable date with Arabic month names and Western digits (`ar-EG-u-nu-latn`, e.g. `21 نوفمبر 2026`).

### Money inputs — `utils/money.js`

Money columns in the DB are `Decimal(18,2)` (customers, suppliers) or `Decimal(18,4)` (product prices, `reorderLimit`). Every money field in a form follows the same rules:

- The form keeps the typed text (`useState` string). Add mode starts at `"0"`; edit mode starts with the API string (`"1500.5"`). An empty field means 0. Exception: a **required** money field (product prices) starts empty in add mode and is checked with "السعر مطلوب" before `validateMoney`.
- Input: `<Input inputMode="decimal" dir="ltr" ... />` (label stays Arabic). Phone, email, tax number and commercial record inputs also get `dir="ltr"`.
- `validateMoney(text, { min, maxDecimals })` in the form's `validate()` → Arabic error or `""`. Checks: a valid number, max `maxDecimals` decimals (default `2`), max `18 - maxDecimals` digits before the point, and `min` when given (mirror the backend: e.g. `{ min: 0 }` for `@Min(0)`, no `min` when negative values are allowed).
- `toMoneyNumber(text, { maxDecimals })` in the page's `<page>Api.js` body builder → a number (`""` → `0`), rounded to `maxDecimals` (default `2`). Money is never sent as a string.
- `Decimal(18,4)` fields pass `{ maxDecimals: 4 }` to all three helpers (see `pages/Products`).

## 7. Shared UI kit — `components/ui/`

Always check this folder before writing UI. Reuse these instead of re-creating them inside pages:

| Component                                  | Use                                                                           |
| ------------------------------------------ | ----------------------------------------------------------------------------- |
| `Button`                                   | variants: `primary`, `secondary`, `danger`, `danger-ghost`, `ghost`; `loading` prop |
| `Input`, `Select`, `Textarea`              | form controls with `label`, `required`, `error`, `readOnly`                   |
| `Modal`                                    | dialog shell: title, body, footer actions; unsaved-changes check (see below)  |
| `ConfirmDialog`                            | delete confirmations ("هل أنت متأكد من حذف ...؟")                             |
| `DataTable`                                | simple table: `columns` + `rows` + optional actions column, horizontal scroll |
| `SearchInput`                              | search box above tables                                                       |
| `Alert`                                    | inline success / error messages                                               |
| `LoadingState`, `ErrorState`, `EmptyState` | the page states (ErrorState has a retry button)                               |

Layout: `MainLayout` (Sidebar + Header + `<Outlet />`), `PageHeader` (title, subtitle, action button slot).

**Unsaved changes in forms** — built into `Modal`, never copy it into a page. Every form modal passes:

- `dirty={isDirty}` → true when the form differs from its starting values. Closing (X / إلغاء / Escape) then first asks "تجاهل التغييرات" ("لديك تغييرات غير محفوظة. هل تريد إغلاق النموذج بدون حفظ؟"). An untouched form closes directly.
- `cancelLabel="إلغاء"` → Modal renders the cancel button itself, so it gets the same check. Do not put your own cancel button in `footer`.
- `closeDisabled={saving}` → X / إلغاء / Escape do nothing while a request is running.
- The submit button lives in `footer` and is linked to the form with `type="submit" form="<form id>"`, so Enter in a field submits too. See `pages/Branches/components/BranchFormModal.jsx`.

Rules: pages never import or render `MainLayout`, Sidebar or Header. Add a new shared component only when a second page needs it; otherwise keep it in the page's `components/` folder.

## 8. Arabic, RTL & design

- `index.html` has `<html lang="ar" dir="rtl">`. Do not add `dir` on components.
- Every user-facing string is Arabic: labels, buttons, placeholders, table headers, empty/error/loading text, confirmations. Use natural, short business Arabic (e.g. "إضافة فرع", "حفظ", "إلغاء", "جارٍ التحميل...").
- API field names stay as they are in code; only the displayed labels are Arabic.
- Prefer logical Tailwind utilities (`ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`, `text-start`) over `ml/mr/pl/pr/left/right`.
- Font: Cairo (loaded in `index.html`, set as `--font-sans`).
- Icons: `lucide-react` only (e.g. `import { Plus, Pencil, Trash2 } from "lucide-react"`). Directional icons (arrows, chevrons) must point the right way in RTL.

### Design tokens (defined once in `src/index.css` with `@theme`)

| Token class                                                               | Meaning                        |
| ------------------------------------------------------------------------- | ------------------------------ |
| `bg-primary`, `hover:bg-primary-hover`, `text-primary`, `bg-primary-soft` | main blue actions / active nav |
| `bg-slate-50`                                                             | app background                 |
| `bg-white` + `border-slate-200`                                           | cards, tables, modals          |
| `text-slate-900` / `text-slate-500`                                       | main / secondary text          |
| `red-600` / `red-700`                                                     | danger                         |
| `green-*`, `amber-*`                                                      | success / warning only         |

Use `primary` tokens instead of `blue-600` so the brand color can change in one place. Style: clean, calm, professional ERP — light shadows, `rounded-lg`, no gradients, no heavy animations. Must work on desktop, laptop and tablet.

### Usability rules (users are accountants, not developers)

- Every clickable element shows a pointer cursor (global rule in `index.css`); disabled shows `not-allowed`.
- Colors have one fixed meaning and are never mixed: blue (`primary`) = main / safe action, red = destructive or leaving (delete, logout), green = success, amber = warning, gray/slate = neutral or cancel. Never use red for a normal action or blue for a destructive one.
- Every destructive or session-ending action (delete, logout, discarding unsaved changes) asks for confirmation with `ConfirmDialog`; the confirm button is red and names the action (e.g. "حذف الفرع", "تسجيل الخروج"), never a vague "تأكيد" or "نعم".
- All interactive elements have clear hover and keyboard focus states.
- Icon-only buttons have an Arabic `title` (tooltip) and `aria-label`, e.g. `title="تعديل"`.
- Buttons use clear Arabic verbs that say what will happen ("حفظ", "إضافة صنف", "حذف").
- Modals close only with X / إلغاء / Escape — never by clicking the backdrop.
- Numbers and dates are shown with Western digits (123).
- Every action gives visible feedback: loading state while waiting, a success message after, an Arabic error if it fails.

## 9. Working rules for Claude Code

- Change only the files the task needs. Never rewrite or "clean up" unrelated pages.
- Do not install packages without asking first (explain why it is needed).
- Not allowed without explicit permission: Redux / Zustand / React Query / form libraries / TypeScript / CSS files per page / new architecture patterns.

Do not run any command that changes git state or GitHub (`git add`, `commit`, `push`, `pull`, `checkout`, `reset`, `merge`, `rebase`, `stash`, `gh ...`) unless Ahmed explicitly asks for it in the current message/prompt. ## 10. Testing

- A task is NOT done until `npm run build`, `npm run lint` and `npm run test:e2e` all pass.
- Every new page gets an e2e test file: the page loads with no console errors, the main happy path works (e.g. list → add → edit → delete with confirmation), and the Arabic error / empty states show.
- Every bug fix gets a regression test that fails before the fix and passes after it.
- Tests fail on any console error or page error coming from the app.
- Never weaken, skip or delete a test to make it pass; fix the real cause.
- Tests that need the backend skip with a clear message when the API is down — tell Ahmed.
- Do not change `../backend` or its data beyond what a test needs through the API.
- In the final report, list: tests run, passed, skipped (and why), and any console warnings seen.
